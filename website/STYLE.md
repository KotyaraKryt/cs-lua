# Как писать документацию cs-lua

Образцы: [AMX Mod X API](https://www.amxmodx.org/api/) и GMod wiki. Справочник, а
не статья. Читатель ищет функцию, а не следит за мыслью автора.

## Страница

```
# Название

Одна строка: что это.

Таблица-индекс всех функций страницы.

## Раздел
таблицы методов, блоки функций
```

## Функция

```
### имя

`имя(arg[, opt])` → `тип`

Одна строка, что делает.

| аргумент | тип | описание |
|---|---|---|
| `arg` | number | что это |

пример кода
```

Блок на функцию — только если у неё есть аргументы или возврат, которые нужно
расписать. Всё остальное — строкой в таблице методов.

## Запрещено

- Абзацы длиннее двух строк.
- Объяснения, почему API устроен именно так.
- Слова «это осознанно», «размен верный», «на практике», «стоит отметить».
- Вводные предложения перед таблицей, если таблица говорит то же самое.
- Обращения к читателю в духе «представь», «когда правка проверяется за пять
  секунд».
- Метафоры и оценки. Только факт и число.

## Ловушки

Поведение, которое ломает код, — одна строка в блоке:

```
> [!WARNING]
> Обращение к состоянию отключённого игрока бросает ошибку. Проверяй `p:connected()`.
```

Синтаксис GitHub: рендерится и на сайте, и в репозитории. Не больше одного блока
на раздел.

## Типы

`number`, `string`, `boolean`, `function`, `table`, `player`, `entity`, `nil`.
Необязательный аргумент — в квадратных скобках: `p:health([v])`.
Геттер-сеттер описывается один раз: «без аргумента читает, с аргументом пишет».

## Код

Примеры минимальные и рабочие. Отступы табами. Комментарий — только если
объясняет неочевидное значение.
